# Code checks

Run the design lint, then review by hand what it cannot read. Report the two apart: a lint result is an exit code and a list of findings; an agent finding is your judgment from the source or the running UI.

## Run the lint

Run `node .claude/design-fleet/run.mjs lint [path]` from the project root. It reads `VISION.md` from that root, so the contract checks below join in when the contract holds their data.

- **Scope, in order:** the path the user gave; the files changed in this session or the diff; the component folder (`components/`, `components/ui/`); the whole project.
- **Files:** a folder scan reads `.tsx`, `.jsx`, `.ts`, `.js`, `.css`, `.scss`, `.vue`, `.svelte` and `.html`. It skips tool and build folders (`node_modules`, `.git`, `.next`, `dist`, `build`, `out`, `coverage` and the like), `prototypes/**`, `evals/**` at the root (where the live suites leave their runs), the globs in the contract's `<!-- qd:lint-ignore -->` section, and files that open with a `GENERATED by` comment. A file named directly is read whatever its extension. Each check still reads only the file types its row names.
- **Exit code:** 1 when there are errors, 2 when the contract or the target is invalid, 0 otherwise. Warnings never fail the run or the edit hook.
- **Baseline:** when `design/fleet/baseline.json` exists, the run fails only on findings beyond the recorded debt and lists the old debt briefly; `design-fleet baseline` records it.
- **Report what the CLI prints:** the files scanned, the files excluded, each suppression and its reason. No finding is not full compliance, and the lint does not see the rendered page.

Lint exclusions belong in the contract, not in one-off tokens: list component galleries, preview art and demo fixtures under `<!-- qd:lint-ignore -->` as gitignore-style globs.

## What the lint checks

The tables below match `makeChecks()` in `lib/lint-rules.mjs`; a test (`tests/code-checks-doc.test.mjs`) fails when they disagree. Severity is the CLI's: an error fails the run and the edit hook blocks a new one; a warning is reported and never blocks. The style checks read plain CSS, React inline style objects and Tailwind utilities with any variant prefix, with comments masked. "Hook" says whether the edit hook runs the check on proposed content: on every edit, only when a new file is written, or never (project checks run with `node .claude/design-fleet/run.mjs lint` only).

### Suppressions

Declared token values let a literal pass V1, V5, V8, V10 and C4; a family the contract declares, or one the global styles or root layout establish, passes T1 and T5; a contract spacing table replaces V7's scale. The CLI prints each suppression with its count and reason, so a quiet run is never silent about why.

## What the reviewer checks

These criteria need judgment from the source or the running UI. Report them as agent review, with the evidence you have; never give them a CLI exit code. Rendered behaviour (focus, keyboard and touch, state changes, reduced motion, overflow, target size) needs the running UI: `node .claude/design-fleet/run.mjs render <file-or-url>` records overflow, target size, focus visibility, reduced motion and console errors at three widths in `.design-fleet/render/<slug>/report.json`. Cite that report; without it, those criteria stay untested.

### Design-system drift

Most drift is visible only against what the project already has. Read `COMPONENTS.md` (or run `node .claude/design-fleet/run.mjs inventory`), the contract's Components and Design tokens tables and the tokens file before judging new UI. Every drift finding names the existing component or token to reuse, by file. The fix is reuse, never a token or variant added on the spot: when the system has nothing that fits, say so and propose one; the user decides.

| ID | Evidence | Check | Look for | Finding |
| --- | --- | --- | --- | --- |
| D1 | Agent review | A raw element or a hand-built widget where a component exists | What N1 cannot see: a `<div onClick>` or an `<a>` acting as a button, a hand-built menu, dialog, tooltip, tabs or toast beside an existing one, a library primitive used bare where the project wraps it, raw controls in HTML pages | Use the existing component (name and file); if it lacks a size or variant, propose one to the user |
| D2 | Agent review | Values off the tokens | What S1 and P1 cannot see: a literal equal to a token value (`#0f172a` where `--ink` holds it), palette and scale classes in a project with no Tailwind v4 theme, arbitrary classes and inline style values for colour, radius, shadow or spacing | Use the token (name it) |
| D3 | Agent review | New custom properties not in the contract | What K3 cannot see: a `--name` defined in a component style sheet, an inline style or another sheet that acts as a token, a new `@theme` key outside the tokens file | Use the existing token; a genuinely new one is proposed in the contract, never added |
| D4 | Agent review | A second component for an existing job | What P15 and P16 cannot see: a new component, in its own file or inside another, that does what an existing one does; a variant prop that repeats an existing variant; a second library for toasts, dialogs or icons | Extend or compose the existing component (name it) |

### Responsive

| ID | Evidence | Check | Look for | Finding |
| --- | --- | --- | --- | --- |
| R1 | Agent review | Zoom stays on | `maximum-scale=1` or `user-scalable=no` in the viewport meta | Never disable zoom |
| R2 | Agent review | Fixed widths | A fixed px `width` on a container or layout element (icons and avatars aside) | Let the layout flex |
| R3 | Agent review | Menus clipped by overflow | `position: absolute` inside an `overflow: hidden` parent | Use a portal, `popover` or the project's menu component |

### Contract judgment

When `VISION.md` describes these, check what a regex cannot. P22 is an error, P20, P21 and P24 are warnings, P23 is info.

| ID | Evidence | Check | Look for | Finding |
| --- | --- | --- | --- | --- |
| P20 | Agent review | Layout conformance | A changed screen whose structure departs from the contract's canonical reference file | Flag the deviation; a new composition on a covered surface needs the user's decision |
| P21 | Agent review | Signature technique | A surface missing the contract's signature technique | Apply it, or flag why not |
| P22 | Agent review | Selection semantics | Re-click and background-click behaviour on pick-one and pick-many groups, when the contract defines it | A required selection never empties by accident |
| P23 | Agent review | Empty-state copy | Collection screens without the contract's empty-state copy | Use the contract's copy |
| P24 | Agent review | App-shell protocol | Screens that skip the contract's shell protocol (footer and overlay state, stable handler references), when it defines one | Follow the protocol |

## Report

Label every finding: lint, agent review, or rendered. Keep the CLI's exit code and severities as printed; never relabel a lint error as a warning because its subject is visual. For agent findings: error for a demonstrated accessibility or interaction failure, warning for a design correction, info for an option. Order errors, then warnings, then info. Quote the code, name the file and line, give a fix that reuses the system.

By default the report is short: what ran, the findings, and what was not checked.

```text
Design lint: src/, 12 files (1 excluded by lint-ignore), exit 1

Lint
- [N1] error  src/app/transactions/page.tsx:73  <button  Use Button (src/components/ui/Button.tsx).
- [V1] error  src/components/ui/Card.tsx:14  rgba(0,0,0,0.15)  Use the shadow token: box-shadow: var(--shadow-card).

Agent review (source-only)
- [D1] warning  src/app/transactions/page.tsx:73  The icon-only delete is a raw button; Button has no icon size. Use Button, and propose an icon size to the user.
- [I7] error  src/components/SaveButton.tsx:22  disabled={saving} on the working control. Use aria-busy and ignore repeat presses.

Not checked
- Rendered focus, touch targets and reduced motion: no running app.
```

When the user asks for the full report, add the agent criteria you reviewed with their evidence, and the ones that do not apply with the reason. Never describe the whole checklist as machine-passed: list the lint's actual checks, scope and exclusions, and the review items still open.

Fixes reuse what exists: a shadow becomes the project's shadow token, a colour its token, a raw control its component. For A3, wrap the app once in `<MotionConfig reducedMotion="user">` (A3 accepts it in a wrapping layout) or branch with `useReducedMotion()`: remove the movement, keep the fade.

## Lint in a build

The lint follows building: build, lint, fix, lint again. Fixing needs an implementation request; a review reports proposed corrections and edits nothing. A rule being active never turns a read-only review into implementation.

## Adding a check

A new executable check needs a concrete pattern from a rule, an implementation in `lib/lint-rules.mjs` with a regression test, and a row in the tables above; the document test fails until the row matches. It must be deterministic: another agent running it on the same code gets the same result. "The spacing feels off" is not a check. "Spacing value `37px` is not on the 4/8/12/16/24/32/48/64 scale" is. Anything that needs judgment is an agent criterion.
